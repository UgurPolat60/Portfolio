Every website runs on a program that listens on a port, reads what the browser sends and writes back an answer. Nearly everyone rents that program — nginx, Apache, whatever the host provides — and treats it as a black box. This is that program, written by hand, so that it isn't one.

Two files, one honest boundary

main.c owns sockets: listen, accept, poll, read, write. It does not know what HTTP is. http.c owns HTTP: parse, route, build a response. It never touches a socket. There is no read() in the HTTP layer and no 404 in the socket layer, and that separation is the whole architecture.

One poll() loop instead of 256 threads

Giving every visitor a thread costs roughly a megabyte of stack each plus constant context switching. Instead, a single poll() call hands the kernel every connection at once and sleeps at zero CPU until one of them speaks. This is the same architectural decision that let nginx displace Apache, and implementing it is very different from reading about it.

The part that is actually hard

TCP is a byte stream, not a message queue. A single HTTP request can arrive in five pieces, and five requests can arrive in one piece. read() does not hand you a request; it hands you whatever turned up. So after every read the server asks one question: is there a complete request in this buffer yet? If not, it waits. If there is, it answers it and shifts whatever came after it to the front of the buffer. Getting this wrong is how servers hang, truncate, or answer the wrong request.

The security boundary

GET /../../../../etc/passwd is the oldest attack on a web server and it has a hundred disguises: %2e%2e, symlinks, nested paths that walk back out. Rather than trying to recognise every disguise, this server doesn't inspect the requested path at all. It hands it to realpath(), which collapses every .. and follows every symlink, and then checks one thing: does the resolved file live inside the document root?

Whatever the client dressed the path up as, after resolution it is either inside or it isn't. There is nothing left to outsmart. The same principle applies to the contact form: every field is decoded, then stripped of control characters, because a newline inside a name would otherwise forge a second entry in the log file.

Knowing where to stop

It does not do TLS — writing your own cryptography is how you acquire a false sense of security; in production this sits behind a proxy that terminates HTTPS. No CGI, no dynamic pages, no database. The contact form appends to a file, which is the correct amount of machinery for a contact form. Deciding what not to build is part of the engineering, not a gap in it.
