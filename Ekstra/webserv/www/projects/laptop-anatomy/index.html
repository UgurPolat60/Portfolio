Anatomy of a Laptop

A laptop that comes apart as you scroll — and every part of it is generated in code, not loaded from a model file.

  • Three.js r180
  • WebGL
  • ES modules + import map
  • Procedural geometry
  • PMREM environment lighting
  • InstancedMesh
  • Scroll-driven camera
  • No build step

Open it and scroll

Eight stages: the closed machine, the display, the deck lifting away, then the processor, the memory, the graphics chip, the cooling assembly, and finally the whole board in an exploded view. Arrow keys and the chapter rail work too, and every stage has its own link.

Needs WebGL — any browser from the last decade has it.

Open the experience →

Almost everyone owns a laptop and almost nobody has opened one. This is a scroll-driven teardown: the machine opens, the keyboard deck lifts away, the cooler comes off, and the camera dives to each component in turn while the text explains what it actually does. The reference machine is a 15.6-inch gaming laptop in the Acer Nitro 5 class — the proportions, component layout and thermal design are taken from that, without the branding.

Nothing was downloaded, everything was built

There is no .glb, no .obj, no model file of any kind. The chassis, the board, the CPU package, the memory modules, the graphics die and its memory chips, the flattened copper heatpipes, the fin stacks, the fans and their thirty-four blades — all of it is boxes, cylinders and instanced meshes positioned in code. It made the whole scene about 45 KB of JavaScript instead of several megabytes of geometry, and it meant the layout could be argued with rather than accepted.

Scroll position is the only input

The page is eight screens tall and the canvas is fixed behind it. How far down you are becomes a number between 0 and 1; everything else is a function of that number — where the camera is, how far the lid has opened, whether the deck has lifted, how far apart the parts have moved. That single value is smoothed rather than followed exactly, which is the whole difference between "3D on a page" and something that feels built.

The teardown had to happen in the right order

The first version dived to the processor and showed a copper plate, because in a real laptop the cooler sits directly on top of the chip. So the cooling assembly now lifts away before the CPU stage and stays off — the same order you would take one apart on a desk. It is a small thing, and it is the difference between a diagram and an explanation.

Making it look like a render rather than a diagram

A polished metal surface has almost no colour of its own — what you see in it is the room. So the scene ships with a room: a studio built out of emissive panels, a big overhead softbox for the streak that runs down the lid, side fills to pick out the edges, baked once into an environment map. Every edge in the model is bevelled rather than sharp, because a bevel is what catches that light and turns an outline into an object.

On top of that sits a post chain: a multisampled buffer, a bloom pass thresholded high enough that only the specular hits glow, ACES tone mapping, and morphological antialiasing to clean the edges. The one thing that took the most tuning was the opposite of adding light — the environment had to be turned down, because at full strength the same panels that make aluminium look like aluminium flood the matte surfaces and a near-black circuit board comes out the colour of sage.

Then it had to actually run

The first version looked right and stuttered. Three things were wrong. There was a full-screen antialiasing pass on top of multisampling that was already doing the same job — three extra passes and two lookup textures for no visible gain. The fan blades were eighty-four separate meshes, which is eighty-four draw calls, doubled again because each one was also drawn into the shadow map. And the shadow map was being redrawn every frame whether anything had moved or not.

So: antialiasing is multisampling alone; the blades and the vents became three instanced meshes; small components still receive shadow but no longer cast it, because a two-millimetre capacitor's shadow is not worth a draw call; and the shadow map is only redrawn when something in it actually moved.

The last piece is a resolution controller. There is no way to ask a browser what refresh rate it is running at, and requestAnimationFrame is capped to it — so a hardcoded 120 fps target would just ratchet the resolution down forever on a 60 Hz screen. Instead the loop watches for the fastest frames it ever manages, takes that as the display's own frame period, and treats "late relative to that" as the signal to render smaller. On a fast machine it climbs back up to full device pixel ratio and spends the headroom on sharpness. It defends whatever the screen can actually show, rather than a number I picked.

Vendored, not linked

Three.js is served from this domain rather than a CDN, because the point of this site is that one C binary serves every byte of it. That also means the page has no third-party requests at all: no CDN, no analytics, no fonts from someone else's server.

Built in code

  • Chassis, deck and hinged lid
  • 10-layer board with VRM and traces
  • CPU package: substrate, die, heat spreader
  • GPU die ringed by its own memory
  • Two SODIMM modules in angled slots
  • Four flattened heatpipes, two fin stacks
  • Two fans, 34 blades each

How it is lit

  • Studio environment baked from emissive panels
  • Bevelled edges on every part
  • Soft shadow maps, shadow-only ground
  • Bloom on the specular hits only
  • ACES tone mapping, morphological AA
  • Brushed-metal anisotropy on the shell

Details that mattered

  • Progress measured from the text, not the scrollbar
  • Labels projected from 3D to screen
  • Linkable stages (#cpu, #board)
  • Honours prefers-reduced-motion
  • Says so on the page if WebGL is missing
Building the laptop out of primitives instead of downloading a model turned a rendering exercise into an argument about where the parts actually go — which is the only reason the page teaches you anything.
